# 13. 독립 개발자 체크리스트

새 프로젝트를 혼자 시작하기 전에, 각 항목이 스스로 "초급 / 중급 / 독립개발 가능" 중 어디에 해당하는지 솔직하게 표시해보라. 이 기준은 BiddingFlow 코드에서 실제로 요구되는 수준을 근거로 만들었다.

## 기본 개발 환경

- [ ] 새로운 Python 프로젝트를 생성할 수 있다
  - 초급: 어디서 시작해야 할지 검색이 필요하다 / 중급: 폴더 구조는 만들 수 있지만 왜 이렇게 나누는지 설명은 어렵다 / **독립개발**: 05번 문서의 "모듈 분리 기준"을 스스로 새 프로젝트에 적용해 폴더 구조를 먼저 설계할 수 있다.
- [ ] 가상환경을 만들고 관리할 수 있다 (`venv`, `.venv`)
  - 초급: 명령어를 매번 검색한다 / 중급: 만들 수는 있지만 왜 필요한지 설명이 어렵다 / **독립개발**: "왜 전역에 패키지를 설치하면 안 되는가"를 다른 사람에게 설명할 수 있다.
- [ ] 라이브러리를 설치하고 `requirements.txt`를 관리할 수 있다
  - 초급: `pip install`만 할 줄 안다 / 중급: `requirements.txt`를 수동으로 관리한다 / **독립개발**: 버전을 고정(pin)해야 하는 경우와 그렇지 않은 경우를 구분한다.

## API/데이터

- [ ] API 문서(또는 코드)를 보고 요청을 작성할 수 있다
  - 기준: `erp_client.py`를 처음 보고 "이 함수들이 실제로 ERPNext에 어떤 요청을 보내는지" 스스로 재구성할 수 있으면 **독립개발** 수준.
- [ ] JSON을 Python dict/list로 자유롭게 처리할 수 있다
  - 기준: 02번 문서 15번 항목의 LLM 응답 파싱 코드(`removeprefix`, `try/except json.loads`)를 보고 "왜 이렇게 방어적으로 짰는지" 설명할 수 있으면 **독립개발**.
- [ ] 환경변수로 설정값을 분리하고, 필수/선택값을 구분해 다룰 수 있다
  - 기준: `os.environ["KEY"]`(필수, 없으면 죽음)와 `os.getenv("KEY", 기본값)`(선택)을 상황에 맞게 스스로 선택해 쓸 수 있으면 **독립개발**.
- [ ] 오류 메시지를 읽고 원인을 스스로 좁혀갈 수 있다
  - 기준: 07번 문서의 "계층을 이분탐색하듯 좁혀라" 방법을 스스로(도움 없이) 낯선 코드에도 적용할 수 있으면 **독립개발**.

## 설계

- [ ] 함수를 목적에 맞게(순수 함수 vs 부작용 있는 함수) 설계할 수 있다
  - 기준: `decide_bidding.py`의 `_direct_purchase_fields`(순수 함수) vs `erp_submit`(부작용 있음, 외부 시스템을 바꿈)의 차이를 구분하고, 새 코드를 짤 때 의식적으로 나눌 수 있으면 **독립개발**.
- [ ] 여러 파일/모듈로 코드를 분리할 수 있다
  - 기준: "이 변경이 다른 파일에 영향을 주지 않는다"는 확신을 갖고 코드를 나눌 수 있으면 **독립개발**.
- [ ] 외부 시스템(다른 API, DB)에 대한 의존성을 한 곳에 모아 캡슐화할 수 있다
  - 기준: `erp_client.py`처럼, "이 시스템을 다른 것으로 바꾼다면 몇 개의 파일을 고쳐야 하는가?"라는 질문에 "1개(또는 소수)"라고 답할 수 있는 구조를 스스로 만들 수 있으면 **독립개발**.
- [ ] 되돌릴 수 없는 부작용(이메일 발송, 결제, 삭제)에 안전장치를 설계할 수 있다
  - 기준: `TEST_MODE`(block_all/custom_only/send_all) 같은 3단계 안전장치의 필요성을 새 프로젝트 시작 시점부터 스스로 떠올릴 수 있으면 **독립개발**. (사고가 난 뒤에야 추가하면 아직 중급.)

## AI/LLM

- [ ] LLM API를 코드에서 호출할 수 있다
  - 초급: 예제 코드를 그대로 따라 실행할 수 있다 / 중급: 프롬프트를 스스로 수정할 수 있다 / **독립개발**: 언제 LLM을 쓰고 언제 규칙(if문)으로 대체해야 하는지 스스로 판단한다(04번 문서 "판단과 제어흐름의 분리").
- [ ] Prompt를 작성할 수 있다
  - 기준: "사실 데이터 + 판단 규칙 + 출력 형식 강제"라는 3단 구조(04번 문서 2절)를 의식적으로 갖춘 프롬프트를 스스로 작성할 수 있으면 **독립개발**.
- [ ] LLM의 출력을 구조화(JSON)해서 받고, 실패에 대비할 수 있다
  - 기준: 파싱 실패 시 예외를 던질지, 빈 값으로 조용히 넘길지를 **상황에 따라 다르게** 선택할 수 있으면(견적 1건일 때 AI 호출을 아예 생략하는 `sq_evaluation.py`처럼) 독립개발 수준.
- [ ] Workflow/그래프 구조가 필요한 시점을 판단할 수 있다
  - 기준: "이 프로젝트는 아직 함수 체인으로 충분한가, LangGraph 같은 프레임워크가 필요한 복잡도인가"를 08번 문서 STEP 6에서처럼 스스로 판단하고 그 판단의 근거를 말할 수 있으면 **독립개발**.
- [ ] Agent라는 용어에 현혹되지 않고 실제 제어 흐름을 코드로 확인할 수 있다
  - 기준: "이게 정말 LLM이 다음 행동을 결정하는 구조인가, 아니면 코드가 고정된 순서로 LLM을 호출하는 것뿐인가"를 04번 문서 10절처럼 스스로 구분할 수 있으면 **독립개발**.

## 데이터/DB

- [ ] 데이터를 DB/API와 연결하고, "원본"과 "화면용 사본"을 구분해 설계할 수 있다
  - 기준: 06번 문서의 "원본은 하나만 둬라" 원칙을 스스로 새 프로젝트에 적용해, 무엇이 source of truth인지 먼저 정할 수 있으면 **독립개발**.
- [ ] 동시성 문제(여러 요청이 같은 데이터를 동시에 바꾸는 상황)를 인지하고 대비할 수 있다
  - 기준: 낙관적 잠금(`version` 컬럼)이나 유니크 제약(멱등키) 같은 장치가 왜 필요한지 스스로 설명하고, 새 프로젝트 설계 시점에 미리 고려할 수 있으면 **독립개발**.

## 프론트엔드

- [ ] 백엔드 API 응답을 프론트 화면 모델로 변환하는 계층을 분리해 설계할 수 있다
  - 기준: `src/procurement/api/cases.ts`의 `caseToMaterialRequest`처럼, "서버가 주는 형태"와 "화면이 필요로 하는 형태"를 분리하는 이유를 이해하고 스스로 그렇게 설계할 수 있으면 **독립개발**.
- [ ] 실시간성이 필요한 기능에 폴링/SSE 중 적절한 것을 선택할 수 있다
  - 기준: "이 정도 빈도/규모라면 SSE가 필요한가, 단순 폴링으로 충분한가"를 01번 문서의 사례를 근거로 판단할 수 있으면 **독립개발**.

## 자기 진단 방법

이 체크리스트를 채울 때, "이 프로젝트(BiddingFlow) 코드를 다시 보지 않고도 같은 판단을 할 수 있는가?"를 기준으로 삼아라. 코드를 봐야만 기억나는 항목은 아직 "중급"이다. **12번 문서의 최종 과제를 도움 없이 완주할 수 있다면, 이 체크리스트의 대부분이 자연스럽게 "독립개발 가능"으로 채워져 있을 것이다.**
