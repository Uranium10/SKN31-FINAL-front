# 11. 새로운 미니 프로젝트 설계 훈련

BiddingFlow와 **기술 스택은 비슷하지만 주제는 완전히 다른** 미니 프로젝트를 처음부터 설계해본다. 이 문서를 따라가며 각 단계마다: (1) 질문에 스스로 답을 적어본다 → (2) 힌트를 읽는다 → (3) 예시 답안을 펼쳐 비교한다. 예시 답안은 "정답"이 아니라 "이렇게도 설계할 수 있다"는 참고일 뿐이다.

**주제**: **"사내 IT 자산(노트북/모니터 등) 대여·반납 자동화 시스템"** — 직원이 자산을 신청하면, 재고 확인 → 승인 필요 여부 판단(고가 자산은 팀장 승인 필요) → 자산 배정 → 대여 계약서 발송 → 반납 기한 관리 → 반납 확인까지 자동화한다. BiddingFlow의 "MR → 비딩판정 → 공급사선정 → RFQ → 견적비교 → PO"와 구조적으로 대응되지만(신청 → 승인판정 → 자산배정 → 계약서발송 → 반납추적), 도메인은 완전히 다르다.

## 1. 요구사항 정의

**질문**: 이 시스템이 해결해야 하는 문제는 무엇인가? 사용자는 누구이며, 무엇을 반복적으로 힘들어하는가?

**힌트**: BiddingFlow의 "00_project_map.md" 2절("사용자 입장에서 해결하는 문제")처럼, "이전에는 어떻게 했는가 → 무엇이 힘들었는가 → 자동화 후 무엇이 바뀌는가"를 한 문단으로 적어보라.

<details><summary>예시 답안</summary>

**문제**: IT 담당자가 엑셀로 자산 대여 현황을 관리하면, 어떤 노트북이 지금 창고에 있는지, 누가 언제까지 빌렸는지, 반납 기한이 지난 자산이 무엇인지 매번 수작업으로 확인해야 한다. 고가 자산(예: 300만원 이상 장비)은 팀장 승인이 필요한데, 이 승인 여부를 담당자가 매번 판단해야 한다.

**사용자**: (1) 신청자(일반 직원) — 자산을 신청하고 반납한다. (2) IT 담당자 — 재고를 관리하고 배정을 확정한다. (3) 팀장 — 고가 자산 신청을 승인/반려한다.

**해결**: 신청이 들어오면 시스템이 자동으로 재고를 확인하고, 금액 기준으로 승인이 필요한지 판정하고, 필요하면 팀장에게 승인 요청을 보내고, 승인되면 IT 담당자가 실물을 배정하도록 안내하고, 반납 기한이 다가오면 자동으로 리마인드를 보낸다. 사람은 "승인/반려"와 "실물 배정 확인"이라는 책임이 필요한 지점에서만 개입한다.
</details>

## 2. 기능 정의

**질문**: 요구사항을 화면 단위 기능 목록으로 쪼개면 무엇이 되는가? (BiddingFlow가 대시보드/MR목록/협력사선정/PO관리로 나뉜 것처럼)

**힌트**: "신청 → 판정 → 배정 → 반납"이라는 단계마다 화면이 필요한지, 아니면 하나의 화면에서 상태만 바뀌는지 먼저 결정하라.

<details><summary>예시 답안</summary>

- **대시보드**: 승인 대기 건수, 배정 대기 건수, 반납 기한 임박 건수 요약
- **자산 신청 목록**: 전체 신청 건 조회, 상태별 필터(승인대기/배정대기/대여중/반납완료)
- **승인 대기함**(팀장용): 고가 자산 신청 승인/반려
- **자산 배정 관리**(IT 담당자용): 실제 재고에서 특정 자산(시리얼 번호)을 배정, 대여 계약서 발송
- **반납 관리**: 반납 기한 임박/초과 목록, 반납 확인 처리
</details>

## 3. 데이터 구조 설계

**질문**: 어떤 데이터가 필요하며, 각 데이터는 어디서 오는가(사용자 입력 / 외부 시스템 / AI 판단 결과)? BiddingFlow의 `PurchaseProcessState`처럼, 이 시스템의 상태를 하나의 구조로 표현한다면 어떤 필드가 필요한가?

**힌트**: 06번 문서의 "어떤 데이터가 ERPNext에서 오는가 / 사용자에게서 오는가 / AI에게 전달되는가"를 그대로 이 도메인에 적용해보라.

<details><summary>예시 답안</summary>

```python
class AssetRequestState(TypedDict, total=False):
    request_id: str
    requester_id: str
    asset_category: str          # "노트북", "모니터" 등
    requested_at: str
    status: str                  # 그래프 진행 상태
    needs_approval: bool
    approval_threshold_price: int
    available_asset_ids: list[str]   # 재고 조회 결과
    assigned_asset_id: str
    approver_decision: str       # "approved" | "rejected"
    rejection_reason: str
    contract_sent: bool
    due_date: str
    returned: bool
    error: str
```
- **자산 마스터/재고**(외부 시스템 또는 자체 DB에서 옴): 자산 종류, 시리얼번호, 현재 상태(창고/대여중/수리중), 구매가
- **사용자 입력**: 신청 사유, 희망 대여기간, 승인/반려 결정, 반납 확인
- **AI 판단**(선택적): "신청 사유가 이 자산 카테고리와 맞는지" 같은 애매한 검증이 필요하면 AI를 붙일 수 있다(7번에서 다룸) — 하지만 "고가 자산 여부"처럼 숫자로 명확한 판정은 AI가 아니라 규칙(if 금액 >= threshold)으로 충분하다(BiddingFlow의 `decide_bidding`이 순수 규칙인 것과 같은 이유).
</details>

## 4. 시스템 아키텍처

**질문**: 이 시스템도 BiddingFlow처럼 "원본 시스템 + 화면용 프로젝션 + 그래프 체크포인트"의 3단 구조가 필요할까? 아니면 더 단순하게 가도 될까? 그 판단 기준은?

**힌트**: 05번 문서의 7번("프로젝트 규모가 커지면...")과 04번 문서의 "LangGraph가 필요해지는 시점"을 다시 떠올려라. "사람이 오래 기다려야 하는 지점이 몇 개인가", "동시 처리량이 얼마나 되는가"가 핵심 판단 기준이다.

<details><summary>예시 답안</summary>

이 자산 대여 시스템은 BiddingFlow보다 **훨씬 단계가 적고(신청→승인→배정→반납, 4단계)**, 사람이 기다리는 지점도 승인 1곳뿐이다. 따라서:
- **회사 규모가 작고 신청 건수가 하루 몇 건 수준**이라면, LangGraph 없이 "상태 컬럼이 있는 테이블 하나 + FastAPI 엔드포인트 몇 개"로 충분할 수 있다(08번 문서 STEP 6의 교훈).
- **여러 부서, 승인 단계가 2단계 이상(팀장→본부장)으로 늘어나거나, 반납 기한 자동 추적/에스컬레이션까지 포함**하게 되면, BiddingFlow와 같은 LangGraph 기반 상태 기계가 정당화된다.
- 이 판단 자체가 "설계 시작 전에 반드시 답해야 할 질문"이라는 게 이 실습의 핵심이다. 아래 5~9번은 "규모가 커진 버전"을 가정하고 진행한다.
</details>

## 5. API 설계

**질문**: 03번 문서에서 배운 REST 원칙(GET/POST, 상태 코드, endpoint 네이밍)을 이 도메인에 적용하면 어떤 엔드포인트가 필요한가?

**힌트**: BiddingFlow의 `/api/procurement/cases`, `/api/procurement/cases/{id}/start`, `/api/procurement/tasks/{id}/answer` 패턴을 참고해 이름만 바꿔보라.

<details><summary>예시 답안</summary>

```
POST /api/assets/requests                    # 신청 생성
GET  /api/assets/requests?status=...          # 목록 조회
POST /api/assets/requests/{id}/start          # 자동 처리 시작(재고확인→승인필요여부 판정)
POST /api/assets/tasks/{task_id}/answer       # 사람의 응답(승인/반려, 배정 확인, 반납 확인)
GET  /api/assets/inventory                    # 자산 재고 목록
GET  /api/assets/events                       # SSE 알림 스트림
```
`{id}/start`와 `tasks/{task_id}/answer`로 나눈 이유는 BiddingFlow와 동일하다: "그래프 실행 시작"과 "사람 입력 재개"는 서로 다른 종류의 행위이므로 엔드포인트도 분리한다.
</details>

## 6. Python 함수 설계

**질문**: "승인이 필요한지 판정하는 함수"를 `decide_bidding.py`의 `_decide_one_item`처럼 순수 함수로 설계한다면 시그니처는 어떻게 될까?

**힌트**: 입력은 무엇이고(자산 가격, 카테고리, 신청자 직급 등), 출력은 무엇인지(bool + 이유) 먼저 적어라. 그 다음 실제로 함수를 작성해보라(코드는 이 훈련의 범위 밖이니 시그니처와 로직 설명만).

<details><summary>예시 답안</summary>

```python
def needs_manager_approval(asset_price: int, category: str, threshold: int = 3_000_000) -> tuple[bool, str]:
    """자산 가격이 기준 이상이거나, 특정 카테고리(예: 서버 장비)면 승인 필요."""
    if asset_price >= threshold:
        return True, f"자산가 {asset_price:,}원 ≥ 기준 {threshold:,}원"
    if category in {"서버", "네트워크 장비"}:
        return True, f"'{category}'는 항상 팀장 승인이 필요한 카테고리"
    return False, "기준 이하 소액 자산, 승인 불필요"
```
`decide_bidding.py`의 `_decide_one_item`처럼 "우선순위가 있는 규칙을 순서대로 검사하고 먼저 맞는 조건에서 반환"하는 스타일을 그대로 따랐다.
</details>

## 7. AI 기능 설계

**질문**: 이 시스템에서 AI(LLM)가 실제로 필요한 지점이 있는가? 있다면 어디이며, 없어도 되는 지점은 어디인가? (04번 문서의 "AI에게 넘길 것 vs 규칙으로 처리할 것" 구분을 적용하라.)

**힌트**: "숫자 비교로 명확히 판단 가능한 것"과 "자연어/문맥 이해가 필요한 것"을 구분하라.

<details><summary>예시 답안</summary>

- **AI가 필요 없는 곳**: 승인 필요 여부(숫자 비교), 재고 확인(단순 조회), 반납 기한 계산(날짜 계산) — 전부 규칙으로 충분하다.
- **AI가 유용할 수 있는 곳**: 신청 사유 텍스트를 보고 "이 신청이 업무 목적에 합당해 보이는가"를 1차 검토하거나(사람의 최종 승인은 유지하되, 애매한 사유에 플래그를 달아주는 보조 역할), 반납 지연 사유(자유 텍스트)를 분류해 "출장 중"/"분실 의심"/"단순 지연" 등으로 태깅하는 것 — `find_substitute.py`가 "재고가 있는 후보 중 실제로 대체 가능한지"라는 애매한 판단만 AI에게 맡긴 것과 같은 원칙이다.
- **AI를 쓰더라도**: 출력은 반드시 구조화(JSON)하고, 파싱 실패 시 안전한 기본값(예: "검토 필요"로 표시)으로 처리한다(04번 문서 8번, `find_substitute.py`의 패턴).
</details>

## 9. 테스트

**질문**: `needs_manager_approval` 함수 하나를 테스트한다면 어떤 입력 조합을 준비해야 "이 함수가 제대로 동작한다"고 확신할 수 있는가?

**힌트**: 경계값(threshold와 정확히 같은 값), 예외 카테고리, 둘 다 해당 안 되는 일반적인 경우를 각각 생각하라.

<details><summary>예시 답안</summary>

| 입력 | 기대 결과 |
|---|---|
| 가격 300만원, 카테고리 "노트북" | `(True, ...)` — 경계값(정확히 threshold)도 승인 필요로 처리되는지 확인 |
| 가격 299만9천원, 카테고리 "노트북" | `(False, ...)` |
| 가격 10만원, 카테고리 "서버" | `(True, ...)` — 가격이 낮아도 카테고리 예외가 우선 적용되는지 확인 |
| 가격 0원, 카테고리 "모니터" | `(False, ...)` |

이 표 자체가 "무엇을 테스트해야 하는가"를 코드를 보지 않고도 도출하는 연습이다. 실제 `pytest` 테스트 함수로 옮기는 것은 어렵지 않다 — **테스트 케이스를 설계하는 사고 과정이 먼저**라는 게 핵심이다.
</details>

## 10. 배포

**질문**: BiddingFlow는 systemd 서비스(`deploy/systemd/*.service`)로 백엔드를 운영하고 nginx로 리버스 프록시한다(도커를 쓰지 않는다). 이 자산관리 시스템도 같은 방식으로 배포한다면, `main.py`에 해당하는 진입점과 `.env`에 반드시 있어야 할 값은 무엇인가?

<details><summary>예시 답안</summary>

- 진입점: `uvicorn main:app --host 0.0.0.0 --port 8001`(BiddingFlow와 포트 충돌을 피하려면 다른 포트)
- 필수 `.env` 값: 자산 마스터 DB 접속정보, 승인 알림용 이메일/슬랙 웹훅 URL, `APPROVAL_THRESHOLD_PRICE`(정책값은 하드코딩하지 않고 환경변수 또는 설정 테이블로 — BiddingFlow의 `AMOUNT_THRESHOLD`가 코드 상수인 것과 달리, 자주 바뀌는 정책이라면 처음부터 환경변수로 빼는 것도 좋은 설계 선택이다), `TEST_MODE`류의 알림 발송 안전장치(신규 프로젝트라면 처음부터 이 안전장치를 넣어라 — BiddingFlow도 "이게 없어서 실제 이메일이 나가버린 적이 있었다"는 교훈을 코드 주석에 남겼다).
</details>

## 마무리

이 훈련의 핵심은 "정답 아키텍처를 외우는 것"이 아니라, **BiddingFlow에서 반복적으로 나타난 설계 질문들("이게 필요한 만큼 복잡한가?", "AI에게 맡길 판단인가 규칙으로 될 판단인가?", "누가 이 결정을 책임져야 하는가?")을 완전히 다른 도메인에도 스스로 던져볼 수 있는가**다. 이걸 할 수 있다면, 세 번째 프로젝트부터는 이 학습 자료 없이도 같은 질문을 스스로 던지게 될 것이다.
