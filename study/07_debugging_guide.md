# 07. 디버깅 가이드

이 문서의 목표는 "이럴 땐 이렇게 고치세요"가 아니라, **"어떻게 원인의 범위를 좁혀가는가"**를 가르치는 것이다. 이 프로젝트는 계층이 뚜렷하게 분리되어 있으므로(05번 문서), 문제가 생기면 **계층을 하나씩 건너뛰며 "여기까지는 정상"을 확인**해 나가면 된다.

## 공통 원칙: 계층을 이분탐색하듯 좁혀라

```
화면(React) → api/*.ts → HTTP → FastAPI 라우터 → 서비스 → LangGraph 노드 → 외부 API(ERPNext/OpenAI/...)
```

무엇이 잘못됐는지 모를 때는 **중간 지점(예: FastAPI 라우터)에서 로그를 찍거나 응답을 확인**해서 "여기까지는 맞다"를 확인한 뒤, 문제가 있는 쪽 절반으로 다시 들어가라. 이 프로젝트에는 이걸 도와주는 지점들이 이미 마련되어 있다:

- `GET /api/health` — 서버가 살아있는지, 폴링 태스크가 도는지(`main.py:366-396`)만 확인. DB/ERPNext 연결은 확인하지 않는다.
- `GET /api/erp_test` — 로그인은 필요하지만 ERPNext 연결 자체만 별도로 테스트(`main.py:399-418`)
- 브라우저 개발자도구 Network 탭 — 프론트가 보낸 요청/받은 응답을 그대로 볼 수 있다(가장 먼저 볼 곳).
- 백엔드 콘솔 로그 — 이 프로젝트의 많은 함수가 `print(f"[...] ...")` 형태로 진행 상황을 출력한다(`decide_bidding.py`, `supplier_search.py` 등). 화려하진 않지만 "지금 어느 단계까지 실행됐는지"를 알기엔 충분하다.

## 1. API가 작동하지 않을 때

**증상**: 버튼을 눌러도 반응이 없거나 에러 토스트가 뜬다.

**좁혀가는 순서**:
1. 브라우저 Network 탭에서 실제로 요청이 나갔는지 확인한다. 안 나갔다면 문제는 프론트 코드(이벤트 핸들러가 안 붙었거나, 조건문에서 걸러짐)다.
2. 요청은 나갔는데 응답이 4xx/5xx라면, **상태 코드로 원인 범위를 좁힌다**(03번 문서의 상태 코드 표 참고): 401이면 인증, 403이면 권한(`_require_case_access`), 404면 대상 없음, 409면 동시성 충돌(버전 불일치), 502면 ERPNext 문제, 503이면 PostgreSQL 문제.
3. 응답 본문의 `detail` 필드를 반드시 읽어라 — 이 프로젝트는 예외 메시지를 한국어로 구체적으로 담아 반환하도록 설계돼 있다(예: `"현재 상태에서는 시작할 수 없습니다: {case['status']}"`). 이 메시지 자체가 원인을 말해준다.
4. 프론트 요청이 아예 다른 서버로 갔을 수도 있다 — `vite.config.js`의 프록시 대상(`VITE_API_BASE_URL`)이 실제로 백엔드가 떠 있는 주소와 맞는지 확인하라.
5. 여기까지도 원인이 안 보이면, 같은 엔드포인트를 `curl`이나 Postman으로 직접 호출해 **프론트를 완전히 배제**하고 백엔드만 테스트하라.

## 2. LLM 결과가 이상할 때 (대체품/견적 순위가 이상하다)

**좁혀가는 순서**:
1. **AI 호출 전 입력이 맞는지 먼저 의심하라.** `find_substitute.py`, `sq_evaluation.py`는 모두 실행 중 `print`로 입력 데이터를 출력한다(`print(f"[견적 수집] '{rfq_name}'에 대해 {len(quotations)}건 견적 수집됨: ...")`). AI가 이상한 답을 낸 게 아니라, **애초에 AI에게 잘못된/불완전한 데이터가 전달됐을 가능성**을 먼저 배제하라.
2. 실제로 AI가 호출됐는지 확인하라. `sq_evaluation.py`는 견적이 1건이면 AI 호출 자체를 생략한다(`if len(quotations) == 1: ... "비교평가를 생략했습니다"`). "AI가 이상한 판단을 했다"고 생각한 게 사실은 "AI가 호출되지도 않았다"인 경우가 있다.
3. 파싱 실패 여부를 확인하라. `except Exception as e: print(f"... AI 응답 파싱 실패: {e}") return []`처럼, 파싱이 실패하면 **에러가 아니라 조용히 빈 결과**로 넘어가도록 설계되어 있다. 콘솔에 "파싱 실패" 로그가 있는지 확인하라 — 있다면 프롬프트나 LLM 응답 형식 문제다.
4. 프롬프트에 실제로 어떤 값이 채워졌는지 확인하라. `PromptTemplate.from_template(...)`에 들어가는 변수(`item_name`, `candidates` 등)를 임시로 `print`해서 "AI가 실제로 무엇을 보고 판단했는지" 재현하라.
5. 그래도 이상하면 모델 자체의 한계일 수 있다 — `temperature=0`으로 설정돼 있어 같은 입력엔 같은 결과가 나오는 게 정상이다(무작위성이 원인일 가능성은 낮다).

## 3. 환경변수가 None일 때

**좁혀가는 순서**:
1. 어떤 변수가 문제인지부터 특정하라. `erp_client.py`의 `SITE_URL = os.environ["SITE_URL"]`처럼 **필수 환경변수는 없으면 서버 시작 자체가 `KeyError`로 죽는다** — 이 경우 에러 메시지에 변수 이름이 그대로 나온다.
2. 서버는 떴는데 특정 기능만 이상하다면, 그 기능이 `os.getenv("VAR", 기본값)`처럼 **선택적 환경변수를 조용히 기본값으로 대체**하고 있을 가능성이 크다. 예: `TEST_MODE`를 안 정해두면 기본값 `"true"`(모든 이메일 차단)로 동작한다 — "RFQ 이메일이 안 나간다"는 증상은 버그가 아니라 **의도된 안전장치**일 수 있다. `get_email_delivery_policy()`를 먼저 확인하라.
3. `.env` 파일이 실제로 로드됐는지 확인하라. `load_dotenv()`는 **현재 작업 디렉터리 기준**으로 `.env`를 찾는다(`main.py`는 `Path(__file__).resolve().parent / ".env"`로 명시적 경로를 쓰지만, `erp_client.py`의 `load_dotenv()`는 인자가 없다 — 실행 위치가 바뀌면 못 찾을 수 있다).
4. 값 자체를 의심하기 전에 "이 변수 이름의 철자가 코드와 `.env`에서 정확히 일치하는가"부터 확인하라 — 오타로 인한 문제가 실제로 가장 흔하다.

## 4. ERPNext 연결이 실패할 때

**좁혀가는 순서**:
1. `GET /api/erp_test`를 호출해 ERPNext 연결만 단독으로 테스트하라(로그인은 필요).
2. 실패 메시지가 `ERPNextAPIError`라면, 메시지 안에 **실제 HTTP 상태 코드와 응답 본문 일부**가 포함되어 있다(`f"GET {doctype}: {res.status_code} - {res.text[:300]}"`). 이 메시지를 그대로 읽으면 원인의 8할은 해결된다 — 401/403이면 API_KEY/API_SECRET 문제, 404면 doctype/문서명 오타, 500이면 ERPNext 서버 쪽 문제.
3. `SITE_URL`이 실제로 접속 가능한 주소인지(브라우저로 직접 열어보거나 `ping`/`curl`) 확인하라 — 네트워크 자체가 막혀 있으면 API 키가 맞아도 실패한다.
4. `erp_submit`에서 "QueryDeadlockError"가 반복된다면, ERPNext 쪽에서 같은 문서에 동시 쓰기가 몰린 것이다 — 코드에 이미 재시도 로직이 있으니(`max_retries=3`), 그래도 실패한다면 ERPNext 서버 자체의 부하 문제일 가능성이 크다.

## 5. 함수가 호출되지 않을 때

**좁혀가는 순서**:
1. **LangGraph 노드라면**, 그 노드로 가는 `goto`가 실제로 실행되는 분기에 있는지 확인하라. `process_commands.py`의 각 함수는 조건에 따라 다른 `goto`를 반환한다 — 디버깅할 땐 각 분기 진입 시 `print`를 추가해 "실제로 어느 분기를 탔는지" 눈으로 확인하는 게 제일 빠르다.
2. **interrupt 노드라면**, 이미 다른 인터럽트에서 멈춰 있어서 이 노드까지 도달하지 못했을 수 있다. `app.get_state(config).next`를 확인하면 "지금 그래프가 어느 노드에서 멈춰 있는지" 알 수 있다 — `workflow_service.py`의 여러 함수가 이 패턴을 쓴다.
3. **API 라우트 함수라면**, `main.py`에서 그 라우터가 실제로 `app.include_router(...)`로 등록됐는지, prefix가 예상과 맞는지 확인하라.
4. **백그라운드 태스크(폴링)라면**, `main.py`의 `lifespan()`이 `MR_INGEST_MODE`에 따라 특정 태스크만 시작한다는 걸 기억하라 — `webhook` 모드에서는 `_poll_material_requests`가 아예 시작되지 않는다(대신 웹훅에 의존). "왜 폴링이 실행 안 되지?"는 사실 "모드 설정이 webhook이라 원래 안 도는 게 맞다"일 수 있다.

## 6. State 값이 비어 있을 때

**증상**: `state["selected_supplier"]`가 예상과 다르게 빈 문자열이거나 없다.

**좁혀가는 순서**:
1. 그 값을 **처음 채우는 노드가 어디인지** 먼저 찾아라(`grep`으로 `"selected_supplier":`를 검색하면 `final_selection_command`, `review_supplier_documents_command`(반려 시 초기화), `handle_pr_rejection_command`(차순위 선택 시 재설정) 등 여러 곳에서 이 값을 쓰고 있다는 걸 알 수 있다).
2. 값이 여러 노드에서 초기화/재설정된다면, **"내가 확인하는 시점이 초기화 이후인지 이전인지"**를 그래프 흐름 순서로 따져보라. 예를 들어 `final_selection_command`는 `"selected_supplier": supplier`로 채우지만, 그 전에 `review_supplier_documents_command`가 반려되면 다시 `"selected_supplier": ""`로 비운다.
3. LangGraph의 `Command(update=...)`는 **전체 상태를 새로 만드는 게 아니라 지정한 키만 병합(merge)**한다는 걸 기억하라. 어떤 노드가 `selected_supplier`를 언급하지 않고 지나갔다면, 이전 값이 그대로 유지된다 — "값이 사라졌다"면 오히려 **어떤 노드가 의도치 않게 빈 문자열로 덮어썼는지**를 의심해야 한다.
4. `workflow_service.py`의 `project_case_from_checkpoint`가 PostgreSQL에 투영한 `workflow_snapshot.values`를 직접 조회해서, "그래프의 실제 상태"와 "화면에 보이는 값"이 일치하는지 비교하라 — 불일치한다면 문제는 State가 아니라 프론트 매핑 함수(`caseToVendorSelectionGroup` 등, `06`/`01`번 문서 참고) 쪽이다.

## 7. API 요청이 실패하면 어떤 일이 생기는가 (설계 관점에서 미리 알아두기)

이 프로젝트는 "실패 시 무슨 일이 생기는가"를 노드마다 명시적으로 설계해뒀다. 디버깅할 때 "지금 이 실패가 설계된 동작인지, 진짜 버그인지"를 구분하려면 이 표를 참고하라(`workflow_service.py`, `process_commands.py` 근거).

| 실패 지점 | 실제로 일어나는 일 |
|---|---|
| `run_queued_case` 안에서 노드가 예외를 던짐 | 케이스 상태가 `FAILED`/`HUMAN_REVIEW`로 바뀌고, 체크포인트의 `next`(재개 가능 지점)가 그대로 보존되어 나중에 "재시도" 가능 |
| `create_rfq_command`가 RFQ 생성 실패 | `Command`로 END에 보내지 않고 **예외를 던져서** 직전 인터럽트(RFQ 대상 선택)에서 다시 응답할 수 있게 함 (주석: "실패 노드를 END로 커밋하면 snapshot.next가 비어 실제 재시도가 불가능하다") |
| `create_po_command`에서 `create_and_send_po`가 `SystemExit` 발생 | 그래프 노드 안에서 `SystemExit`을 잡아 `RuntimeError`로 바꿔서 정상적인 `human_review`로 전환(원래 독립 CLI 스크립트였던 함수를 그래프에 편입하며 생긴 예외 변환) |
| 알림 생성(`_create_notification_safely`) 실패 | 본 업무(구매 처리)는 성공한 채로 유지하고, 알림 실패만 로그로 남김 — "부가 기능의 실패가 핵심 기능을 롤백시키지 않는다" |
| 체크포인트 삭제(`_delete_thread_checkpoint_safely`) 실패 | 마찬가지로 케이스 상태 전이를 롤백하지 않음 |

**일반 원칙**: 실패했을 때 "전체를 롤백할 것인가, 부분만 실패로 표시하고 계속할 것인가"를 미리 정해두지 않으면, 장애가 났을 때 코드를 처음부터 다시 읽으며 판단해야 한다. 이 프로젝트는 **"핵심 트랜잭션과 부가 채널(알림, 로깅, 캐시 정리)을 분리해서, 부가 채널의 실패가 핵심을 막지 않게 한다"**는 원칙을 일관되게 적용한다.

## 8. 디버깅 자체에 대한 마지막 조언

- **에러 메시지를 끝까지 읽어라.** 이 프로젝트는 대부분의 예외 메시지에 "무엇이, 왜" 실패했는지 한국어로 구체적으로 적어둔다. 메시지를 무시하고 코드부터 뒤지는 건 시간 낭비다.
- **"설계된 안전장치"와 "버그"를 헷갈리지 마라.** `TEST_MODE`로 이메일이 안 나가는 것, 견적 1건일 때 AI 비교가 생략되는 것, 낙관적 잠금으로 409가 나는 것은 전부 **의도된 동작**이다. 먼저 주석과 이 프로젝트의 학습 문서(04, 05, 06번)를 다시 확인해서 "이게 원래 이래야 하는 동작인가"부터 판단하라.
- **재현 가능한 최소 단위로 좁혀라.** `decide_bidding.py`, `find_substitute.py`, `erp_client.py`는 전부 `if __name__ == "__main__":`으로 단독 실행이 가능하다. 전체 웹 서버를 띄우지 않고도 이 스크립트들을 CLI로 직접 실행해 "이 함수 하나만" 테스트할 수 있다 — 이게 왜 유용한 설계인지는 08번 문서(직접 만들어보기)에서 다시 다룬다.
